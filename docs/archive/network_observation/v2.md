# Network Telemetry & Device Behavior Enrichment — Implementation Plan

## 0. Purpose (read this first)

We currently have a working packet listener on the client that captures raw
packets (ARP, DHCP, mDNS, LLMNR, NBNS, SSDP, TCP/UDP, etc.) and writes them to
a single flat JSON array per day. That works as a proof of concept but does
not scale to 25 clients running continuously, and it isn't in a shape the
future ML team can use.

This plan replaces the flat packet dump with a layered pipeline:

```
packets -> flows -> 5-min device enrichment -> 15-min activity windows -> delta sync to server
```

Raw packets stay on the client. The server only ever receives compact,
changed-only summaries, plus full flow detail on demand.

**Non-goals for this iteration (explicitly out of scope — do not implement):**
- No location / positioning logic of any kind.
- No ML / anomaly scoring / risk scoring. This phase only produces clean
  telemetry; scoring is a later project by another team.
- No sending of raw packets to the server, ever.
- No full device-base re-send every cycle — only deltas.

## 2. Client-side storage layout

```
client/storage/
└── network_telemetry/
    └── 2026-09-02/
        ├── packets/
        │   ├── tcp.json
        │   ├── udp.json
        │   ├── arp.json
        │   ├── mdns.json
        │   ├── llmnr.json
        │   ├── nbns.json
        │   ├── ssdp.json
        │   └── dhcp.json
        ├── flows.json          # finalized (expired) flows, appended
        ├── devices.json        # local device base (identity + presence + discovery)
        └── activity/
            ├── 11-00_11-15.json
            ├── 11-15_11-30.json
            └── ...
```

Protocol subfolders are an output/organization detail of one classifier, not
separate capture engines — see component 4 below.

Add file rotation/size limits per day per protocol file (config value, e.g.
50 MB or N packets) so one noisy client can't blow up disk usage. When a
limit is hit, roll to a new numbered file (`tcp.1.json`, `tcp.2.json`, ...).

## 3. Data schemas

### 3.1 Packet observation (unchanged in spirit, keep as-is)
Keep every field you're already capturing: `timestamp`, MAC/IP, ports,
protocol, `packet_length`, `tcp_flags`, `direction` (where determinable),
`interface`, and `protocol_metadata`. Add one new required field:

```json
"observer_client_id": "client_07"
```

This must never be `null` once the client is registered with the server.

### 3.2 Flow record (produced by the Flow Aggregator, on flow expiry)

```json
{
  "flow_id": "client_07-1725282922495",
  "observer_client_id": "client_07",
  "first_seen": "2026-09-02T13:35:22.495Z",
  "last_seen": "2026-09-02T13:37:27.123Z",
  "src_mac": "E4:FD:45:BA:8B:96",
  "src_ip": "172.16.2.246",
  "dst_mac": "AC:71:2E:FA:88:3F",
  "dst_ip": "43.163.42.171",
  "src_port": 61488,
  "dst_port": 443,
  "protocol": "TCP",
  "application_protocol": "HTTPS",
  "direction": "outbound",
  "packet_count": 843,
  "bytes": 482931,
  "duration": 124.628,
  "avg_packet_size": 573.0,
  "min_packet_size": 54,
  "max_packet_size": 1514,
  "tcp_syn": 1,
  "tcp_fin": 1,
  "tcp_rst": 0,
  "inbound_packets": 214,
  "outbound_packets": 629,
  "inbound_bytes": 138921,
  "outbound_bytes": 344010,
  "avg_inter_arrival_time": 0.148
}
```

A flow expires (is finalized and written) after ~30–60s of no matching
packets — make this a config value (`FLOW_IDLE_TIMEOUT_SECONDS`).

### 3.3 Local device record (5-minute enrichment — identity/presence only)

```json
{
  "mac": "e4:fd:45:ba:8b:96",
  "ip": "172.16.2.110",
  "hostname": "DESKTOP-XYZ",
  "vendor": "Dell",
  "os_guess": null,
  "first_seen": "2026-09-02T08:12:03Z",
  "last_seen": "2026-09-02T13:37:27Z",
  "discovery": {
    "dhcp": { "seen": true, "last_seen": "..." },
    "mdns": { "seen": true, "last_seen": "...", "services": ["_nsdswc._tcp.local"] },
    "llmnr": { "seen": true, "last_seen": "..." },
    "nbns": { "seen": true, "last_seen": "...", "name": "WPAD" },
    "ssdp": { "seen": false, "last_seen": null }
  }
}
```

This job **must not** invent activity numbers. If nothing was observed, leave
`discovery` fields as `seen: false` and don't touch `last_seen` for that
device. This job only updates identity/presence/discovery — never flow stats.

### 3.4 Activity window (15-minute — per device, consumed from flow data already aggregated, not re-scanned from packet files)

```json
{
  "device_mac": "e4:fd:45:ba:8b:96",
  "window_id": "2026-09-02T11:00:00Z_11:15:00Z",
  "window_start": "2026-09-02T11:00:00Z",
  "window_end": "2026-09-02T11:15:00Z",
  "active": true,
  "flow_count": 37,
  "packet_count": 4218,
  "bytes": 2384912,
  "protocols": { "TCP": 3200, "UDP": 1018 },
  "ports": { "443": 9, "53": 2, "80": 1 },
  "connections": { "internal": 24, "external": 13 },
  "unique_destinations": 12
}
```

If a device had zero flows in the window, still emit a record with
`active: false` and all counters at `0` — absence of activity is itself
signal for the later ML team. Don't just omit the device.

`window_id` is the idempotency key (see §5).

### 3.5 Client → Server sync payload (every 15 min, delta only)

```json
{
  "client_id": "client_07",
  "sync_timestamp": "2026-09-02T11:15:03Z",
  "window_id": "2026-09-02T11:00:00Z_11:15:00Z",
  "updated_devices": [
    {
      "mac": "e4:fd:45:ba:8b:96",
      "ip": "172.16.2.110",
      "hostname": "DESKTOP-XYZ",
      "vendor": "Dell",
      "os_guess": null,
      "last_seen": "2026-09-02T13:37:27Z",
      "discovery": { "...": "..." },
      "activity": { "...activity window object from 3.4..." }
    }
  ]
}
```

Only include devices whose identity/presence changed **or** that had an
activity window (active or explicitly inactive) in this sync cycle. Unchanged
devices with no activity are omitted entirely.

### 3.6 On-demand flow detail (server → client request, client → server response)

```
GET /clients/{client_id}/devices/{mac}/flows?window=2026-09-02T11:00:00Z_11:15:00Z
```

Response: array of full flow records (§3.2) matching that device and window,
served from the client's local `flows.json`. This is the only path through
which raw flow-level detail leaves the client.

## 4. Components to implement

| Component | Runs on | Responsibility |
|---|---|---|
| Network Neighborhood Reporter | client | Sends initial device list to server once, on connect/registration |
| Packet Capture | client | Continuous raw capture |
| Protocol Classifier + Scope Filter | client | Tags protocol, applies subnet scope filter (see §6), writes to `packets/<protocol>.json` |
| Flow Aggregator | client | Maintains in-memory active flows, finalizes to `flows.json` on idle timeout |
| Device Enrichment Job | client | Every 5 min: updates `devices.json` identity/presence/discovery only |
| Activity Window Aggregator | client | Every 15 min: reads finalized flows since last window, groups by device, writes `activity/<window>.json` |
| Sync Manager | client | Every 15 min: builds delta payload (§3.5), POSTs to server, retries with backoff on failure using `window_id` as idempotency key |
| Server Merge Service | server | Receives deltas, upserts into global device inventory, stores activity summaries, dedupes by `window_id` |
| On-demand Flow API | server + client | Server relays flow requests to the originating client; client serves from local `flows.json` |

---

## 5. Timing & idempotency

| Task | Interval |
|---|---|
| Packet capture | continuous |
| Flow finalization | on idle timeout (~30–60s, configurable) |
| Device enrichment (identity/presence) | 5 min |
| Activity window aggregation | 15 min |
| Delta sync to server | 15 min (aligned with activity window) |
| Daily rotation / packet file limits | continuous, size-based |

Every activity window and every sync payload carries a `window_id`
(`<start>_<end>` ISO timestamps). The server treats `window_id` per device
as an idempotency key — re-sends after a failed ACK must not create
duplicate activity records. Sync Manager retries on failure; server responds
with ACK/NACK per `window_id`.

---

## 6. Subnet scope filtering (for the distributed-capture phase)

Each client is assigned one or more CIDR ranges by the server at connect
time (not hardcoded in the client):

```json
{
  "client_id": "client_07",
  "observation_scope": ["172.16.2.0/26"]
}
```

Filter rule — keep a packet if **either** side is in scope:

```
keep = (src_ip IN observation_scope) OR (dst_ip IN observation_scope)
```

Apply this filter right after protocol classification, before writing to
per-protocol packet files and before flow aggregation.

## 7. Implementation phases (in order)

1. **Schema + storage scaffolding** — create the folder layout in §2, add
   `observer_client_id` to existing packet records, add file rotation.
2. **Flow Aggregator** — in-memory flow table, idle-timeout finalization,
   append to `flows.json` per §3.2.
3. **Scope filtering** — server assigns `observation_scope`, client applies
   the filter in §6. (Can be developed in parallel with #2.)
4. **Device Enrichment Job (5 min)** — build/update `devices.json` per §3.3,
   sourced from discovery protocol observations only.
5. **Activity Window Aggregator (15 min)** — consume `flows.json` since last
   window (don't re-scan raw packets), group by device MAC, emit §3.4
   records, including explicit zero-activity records.
6. **Sync Manager** — build delta payload (§3.5), send to server, implement
   retry + idempotency via `window_id`.
7. **Server Merge Service** — upsert devices, store activity windows keyed
   by `(device_mac, window_id)`, dedupe on repeat delivery.
8. **On-demand Flow API** — server endpoint that proxies to the relevant
   client; client endpoint that serves matching records from `flows.json`.
9. **Initial connection / Network Neighborhood** — if not already wired to
   this new schema, connect it so it seeds the server's device inventory on
   client registration.

---

## 8. Acceptance criteria

- No raw packets ever leave the client; only §3.5 deltas and §3.6 on-demand
  flow responses cross the network.
- A device with zero activity in a 15-min window still produces a record
  with `active: false`, not a missing record.
- Killing and restarting the client mid-window does not create duplicate
  server-side activity records for the same `window_id`.
- Disk usage for packet files is bounded by rotation limits, verified over a
  multi-hour soak test on one client before rolling out to all 25.
- Scope filter correctly retains traffic where the client's assigned subnet
  is on either the source or destination side.
- No location fields, no ML/scoring fields, and no full-device-base resend
  appear anywhere in the sync payload.
