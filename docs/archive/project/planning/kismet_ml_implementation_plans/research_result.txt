ML Dataset & Feature Requirements for Kismet Wireless Intelligence
Executive Summary & Phase 0 Architectural Alignment
The wireless investigation system under development utilizes a single Linux server hosting Kismet as its exclusive wireless capture sensor1. In this architecture, the Linux server manages all radio frequency capture, storing raw data locally in SQLite .kismet database files1. The service layer (server_components/kismet_service.py) accesses these database files in a read-only mode to expose normalized wireless observations1.
Currently, the normalized observation layer processes basic 802.11 metadata, including frame type and subtype, Media Access Control (MAC) address roles (source, destination, transmitter, receiver, BSSID), signal strength (RSSI), channel frequency, packet length, sensor identifier, and capture-file provenance1. Control frames are suppressed by default in the primary observation path to reduce storage overhead, and raw Kismet database retention is set to 48 hours1.
This operational architecture imposes strict constraints on the Machine Learning (ML) data foundation:
Production inference must execute on the single Linux host using CPU resources without degrading Kismet’s frame-capture loop.
Model training occurs offline, requiring Phase 0 to extract and persist a feature set rich enough to support model development without requiring full packet payload duplication or decryption.
Raw Kismet capture files remain the single source of truth; ML components must consume derived observations, windowed statistics, and structured feature vectors.
An evaluation of public benchmark datasets across device fingerprinting, traffic activity classification, cryptomining detection, and wireless intrusion detection yields a clear engineering requirement: Phase 0 must expand its metadata extraction layer. Default suppression of management frame Information Elements (IEs), sequence numbers, retry flags, control frame metrics, and fine-grained frame timing patterns degrades signal quality required for persistent identity linking and threat detection3.
Phase 0 must evolve from a basic packet-metadata stream into a multi-tiered observation engine. This engine must capture management frame Information Elements, preserve frame timing and directional attributes, and aggregate traffic into sliding temporal windows.
Device Fingerprinting Dataset Analysis
Device fingerprinting in 802.11 networks aims to establish persistent physical device identities across temporal boundaries, even when devices utilize IEEE 802.11aq/ax Media Access Control (MAC) address randomization3. The primary engineering goal is identity linking (clustering observations from the same physical hardware) rather than static vendor or model classification3.

Raw Field & Information Element Granularity
Inspecting the downloadable packet structures of these datasets shows that MAC de-randomization relies on specific Information Elements (IEs) contained within 802.11 Probe Request and Association Request management frames3.
802.11 management frames contain header fields alongside a variable-length sequence of tagged Information Elements:
Header Metadata: Contains 12-bit Sequence Control numbers, Frame Control flags (Retry, More Data), precise arrival timestamps, and Radiotap RSSI/channel metrics3.
Ordered IE Tag Sequence: The specific ordered array of IE tag IDs present in a frame serves as a static signature of the client's wireless network interface card (NIC) driver and OS network stack5.
Capabilities Bitmasks:
Supported Rates (Tag 1) and Extended Supported Rates (Tag 50)8.
HT Capabilities (Tag 45): Supported channel widths, A-MPDU parameters, spatial stream capabilities8.
VHT Capabilities (Tag 191): Very High Throughput MCS sets, Beamformer capabilities8.
HE Capabilities (Tag 255 / Extension 35): High Efficiency (Wi-Fi 6) MAC/PHY capability bitmasks8.
RSN Information (Tag 48) & WMM Capabilities (Tag 221, OUI 00:50:f2, Type 2).
Vendor-Specific IEs (Tag 221): Contains Organizationally Unique Identifiers (OUIs) and custom vendor payload bytes (e.g., Apple, Broadcom, Microsoft, Samsung extensions)5.
802.11 Sequence Numbers: The 12-bit sequence number field in the 802.11 Frame Control header. Operating systems implement sequence counter updates differently when randomizing MAC addresses. Some drivers maintain a global sequence counter across randomized and factory MACs, producing a continuous linear sequence that exposes address rotation6.
Ground-Truth Labels for Identity Linking
In the Mendeley Probe Request dataset, every frame is mapped back to the true physical device hardware instance, regardless of how frequently the device rotated its randomized MAC address or modified its transmission power3. This ground truth enables training models for identity linking (learning pairwise similarity metrics between frame bursts)3.
In contrast, datasets labeled solely by observed MAC address or vendor OUI cannot train models to cross MAC randomization boundaries, making them unsuitable for physical device linking3.
Kismet Reproducibility Assessment
Kismet captures raw frames via libpcap/Linux mac80211 monitor interfaces and stores structured representations inside the devices table (in JSON blobs under dot11.device) and frame records inside the packets table of .kismet SQLite files1.
While raw captures contain all management frame fields, Kismet's default REST API and internal normalized device structures aggregate or discard raw IE byte arrays to save memory2.
To support physical device identity linking, Phase 0 must explicitly parse and extract raw IE byte strings, tag order vectors, and sequence numbers directly from the packets table payload blob or extend kismet_service.py to extract dot11.probreq.ie JSON attributes prior to aggregation2.

Feature Extraction Without Decryption
Activity classification over encrypted Wi-Fi networks relies on physical-layer and MAC-layer framing characteristics:
Directional Attribution (To-DS / From-DS): The Frame Control header contains two bits (To-DS and From-DS). In infrastructure networks:
To-DS = 1, From-DS = 0: Client Uplink transmission.
To-DS = 0, From-DS = 1: Client Downlink transmission. This enables exact computation of uplink/downlink packet and byte ratios without reading IP headers.
Frame Length Distributions: Video streaming produces asymmetric traffic with bimodal packet size distributions (small uplink ACKs ~100 bytes, large downlink data frames ~1500 bytes). File transfers exhibit sustained maximum transmission unit (MTU) frames on downlink or uplink. Interactive web browsing produces bursty, variable-length frame clusters.
Inter-Arrival Time (IAT) Statistics: Real-time traffic (VoIP, video calls) exhibits tightly bounded IAT variance. Web browsing shows long idle intervals punctuated by rapid burst clusters.
Representation Architecture Trade-Offs
The structural representation selected for Phase 0 directly impacts feature extraction stability, inference latency, and computational memory footprint on a single Linux host:
Packet-Based Representation: Processes individual frame events sequentially. While simple, it creates extreme CPU processing overhead during high-throughput bursts and lacks broader temporal context.
Flow-Based (5-Tuple) Representation: Groups frames by source IP, destination IP, source port, destination port, and transport protocol. This model fails on unencrypted 802.11 monitor feeds because layer-2 WPA2/WPA3 encryption hides layer-3 and layer-4 headers.
Fixed Temporal Window Representation: Aggregates all MAC frames associated with a client over non-overlapping time intervals (e.g., every 30 seconds). This approach reduces CPU load but can miss state transitions that cross window boundaries.
Sliding Temporal Window Representation (Recommended): Aggregates client MAC frames over a fixed temporal duration (e.g., 30 seconds) that advances at a smaller step interval (e.g., 5 seconds). This structure provides continuous state tracking, smooths temporal transition boundaries, and operates directly on layer-2 MAC metadata without payload decryption.
The Sliding Temporal Window constructed at the client MAC level is the most defensible representation for a Kismet-only deployment.
Cryptomining Traffic Analysis
Cryptomining detection requires identifying consensus protocol traffic (e.g., Stratum) embedded within standard network flows. Cryptomining detection is evaluated separately from general activity classification due to its unique network footprint and threat profile.
Stratum Protocol Dynamics & Benchmark Datasets
Evaluation of datasets such as the Mendeley Cryptojacking Network Traffic 2021 (CNT21) reveals the behavioral characteristics of cryptocurrency mining traffic:
Stratum Architecture: Mining clients communicate with pool servers using JSON-RPC over TCP, TLS, or WebSockets.
Traffic Volumetrics: Cryptomining requires negligible bandwidth compared to video streaming or file downloads. An active miner transmits small work-request and share-submission packets at periodic intervals.
Payload Encryption: Even when Stratum traffic is wrapped in TLS (port 443) or transported over encrypted WPA2/WPA3 Wi-Fi, the protocol's underlying synchronization patterns remain visible in metadata.
Stratum mining exhibits a distinct layer-2 metadata signature. Downlink frames from the pool server containing new job assignments or difficulty targets typically range from 300 to 500 bytes. Uplink share submission frames from the client miner range from 150 to 250 bytes. Inter-arrival timing displays rigid periodicity driven by keep-alive timers and share submission intervals, producing a volumetric profile characterized by low total byte counts, near-zero frame size variance, and high session persistence.

Wireless Threat & Intrusion Dataset Analysis
Wireless threat detection targets malicious or anomalous protocol behaviors operating at the IEEE 802.11 physical and MAC layers4.
AWID / AWID2 / AWID3 Benchmark Analysis
The Aegean Wi-Fi Intrusion Dataset (AWID) family, culminating in AWID3, represents the benchmark standard for 802.11 intrusion detection research4. AWID3 captures modern enterprise topologies incorporating WPA2/WPA3, 802.1X Extensible Authentication Protocol (EAP), and 802.11w Protected Management Frames (PMF) across 254 standardized features and raw PCAP captures4.

Phase 0 Extraction & Storage Specification
Phase 0 must extract, transform, and store raw capture data to supply downstream ML capabilities.
Raw Observation Requirements
The system must modify the kismet_service.py extraction pipeline to preserve raw observation fields directly from Kismet SQLite databases1. Suppressing control frames by default conceals attacks like RTS/CTS jamming22. Phase 0 must maintain a dual-path pipeline: high-frequency rate monitoring for control frames and structured extraction for management and data frames.
The dual-path observation extraction architecture processes data from Kismet SQLite capture files (packets and devices tables)1. Path A functions as a Control Frame Rate Engine, suppressing full payload storage while aggregating high-frequency rate metrics into 1-second interval counters to output Threat Window Schemas. Path B operates as a Structured Observation Engine, parsing 802.11 management and data headers, extracting ordered IE vectors, and maintaining per-MAC temporal buffers to generate Fingerprint and Activity schemas.

Traffic Window Schema (Activity & Mining)
Evaluations of temporal aggregation windows demonstrate trade-offs across feature stability and detection latency:
15-Second Windows: Captures short bursts, but exhibits high variance for low-frequency activities like periodic background sync.
30-Second Windows (Recommended Initial Standard): Provides an optimal balance between statistical stability for flow features (mean packet size, inter-arrival variance) and acceptable detection latency for user state transitions.
60-Second Windows: Smoothes activity variations, but delays threat and state transition detection.
Recommended Configuration: 30-second sliding temporal window with a 5-second hop step.

Dataset Labeling Strategy
Supervised offline training requires a clear labeling taxonomy across all target ML capabilities:
Device Fingerprinting Labels:
Primary Target: Physical Device Hardware ID (Unique GUID assigned to a single physical device instance).
Auxiliary Targets: Vendor OUI Class, Operating System Family (iOS, Android, Windows, Linux, IoT).
Device Activity Labels:
Single Target Classes: {idle, browsing, streaming, file_transfer, chat, voip, p2p, other}.
Threat Detection Labels:
Single Target Classes: {normal, deauth_flood, disassoc_flood, scanning, rogue_ap, power_save_injection, anomaly}.
Mining Detector Labels:
Binary Target: {mining, non_mining}.
Label Categorization & Verification
Label types must be explicitly tracked in the dataset repository:
Ground-Truth Labels: Manually verified hardware identities and controlled traffic generation logs (e.g., automated test harness execution).
Weak Labels: Inferred labels derived from high-confidence heuristic rules (e.g., labeling an unencrypted HTTP GET request containing User-Agent strings as an auxiliary OS signal).
Derived Labels: Output generated from baseline clustering algorithms subjected to manual review.
Manually Reviewed Labels: Human-in-the-loop analyst confirmations generated via inspection tools.
Multi-Label Classification Strategy
While Activity Classification operates primarily as a multi-class problem (selecting the dominant traffic profile per 30-second window), actual network traffic can exhibit concurrent activity (e.g., background file download during a VoIP call).
The Phase 0 schema must support Multi-Label Probability Vectors, enabling models to emit independent probability distributions across activity classes rather than forcing a single mutually exclusive argmax label.
Leakage-Safe Training & Evaluation Strategy
Data leakage is a common cause of degraded generalization performance in wireless ML models.
Two primary leakage vectors affect wireless ML pipelines:
Temporal Leakage (Sliding Window Contamination): Occurs when overlapping temporal windows (e.g., Window  spanning 0–30s and Window  spanning 5–35s) are randomly assigned across train and test splits, leaking identical packet patterns into evaluation sets.
Identity / Device Leakage: Occurs when frame bursts originating from the same physical device (under different randomized MACs) are split between training and evaluation partitions, artificially inflating fingerprinting accuracy.
To prevent leakage, Phase 0 must implement a Group-Based Splitting Strategy, where the group key is defined as (Physical Device GUID + Capture Session ID + Calendar Day). Entire groups are assigned exclusively to Train, Validation, or Test splits.
Evaluation Strategies per Capability
Fingerprinting & Identity Linking:
Split Strategy: Group-K-Fold by (Physical Device GUID, Capture Session). No device present in the training set may appear in the evaluation set.
Core Metrics:
False Merge Rate (FMR): Rate at which two distinct physical devices are incorrectly assigned to the same identity cluster.
False Split Rate (FSR): Rate at which observations from a single device are fragmented into separate clusters.
Adjusted Rand Index (ARI) and Normalized Mutual Information (NMI) for global partition evaluation.
Activity & Cryptomining Classification:
Split Strategy: Stratified Group-K-Fold grouped by (Client MAC, Session Day). Prevents adjacent sliding temporal windows from overlapping across splits.
Core Metrics:
Macro F1-Score: Balances performance across rare classes (e.g., P2P) and dominant classes (e.g., browsing).
Precision-Recall Area Under Curve (PR-AUC): Evaluates performance under class imbalance.
Confidence Calibration (Expected Calibration Error - ECE): Ensures generated probabilities accurately reflect actual confidence.
Threat Detection:
Split Strategy: Time-based block splitting. Train on historical capture days; test on subsequent future days. Prevents temporal autocorrelation leakage.
Core Metrics:
False Positive Rate (FPR) per Hour: Operational mandate requiring  false alarms per hour in clean environments.
Detection Latency: Elapsed time from the start of an attack frame sequence to model alert generation.
Domain Gap Analysis & Transfer Learning
Public benchmark datasets are captured in controlled lab environments using specific radio hardware, which differs from real-world Kismet sensor deployments.
Comparing public benchmarks against a production Kismet environment highlights key operational gaps:
Receiver Hardware: Public benchmarks often use specialized NICs (e.g., Atheros AR9271), whereas production hosts use commercial adapters (e.g., Alfa AWUS036ACH).
Channel Visibility: Benchmarks typically record on a single fixed channel (e.g., Channel 6), whereas production sensors perform multi-channel hopping sweeps.
Packet Loss & Framing: Lab captures exhibit low packet loss (), whereas wild environments experience higher loss () and partial frame visibility.
Background Noise: Benchmarks feature low client density, whereas target production environments operate in crowded ISM bands.
Strategic Dataset Roles
To bridge the domain gap without retraining models from scratch:
Pretraining & Feature Extraction: Public datasets (AWID34, ISCX201618, UJI Probes8) should be used to pretrain offline feature extractors and establish baseline representations.
Feature Engineering Validation: Verify that derived feature formulations (e.g., periodicity scores, directional ratios) successfully separate classes on public benchmark data.
Production Fine-Tuning: Models deployed to production hosts must be fine-tuned using locally captured, domain-specific training data to account for local radio hardware, channel hopping artifacts, and local noise profiles.

Model Architecture Recommendations
Production inference must run on a single Linux server alongside the core Kismet capture process, favoring computationally efficient, explainable model families over deep neural networks.
Model selection trade-offs evaluate tabular performance, inference latency, memory footprint, and CPU overhead on a single Linux host:
LightGBM / XGBoost (Gradient Boosted Trees): High accuracy on tabular features, low CPU inference latency (), small memory footprint, handles missing values natively. Highly recommended for production.
Random Forest: Strong baseline, highly parallelizable, but produces larger model binary sizes and slightly higher inference latency than LightGBM.
Logistic Regression: Extremely low latency and minimal memory footprint, but struggles with non-linear feature interactions.
Deep Neural Networks (CNN/LSTM/GRU): High benchmark performance on sequential raw data, but requires high CPU/GPU compute, large memory footprint, and acts as a black box. Not recommended for host-constrained single-server inference.
Isolation Forest: Unsupervised tree structure with minimal computational overhead. Ideal for detecting zero-day protocol anomalies.
Recommended Production Model Families
Capability 1: Identity Linking & Fingerprinting:
Model Family: Hybrid IE Sequence Vectorizer + LightGBM Pairwise Distance Model + Agglomerative Hierarchical Clustering.
Rationale: Tree-based gradient boosting models handle categorical Information Element bitmasks efficiently. The model evaluates whether two frame observations originate from the same physical device, outputting a similarity score that feeds a real-time clustering engine.
Capability 2: Device Activity Classification:
Model Family: LightGBM Classifier operating on 30-second sliding window aggregate features.
Rationale: LightGBM provides low inference latency ( per window) on multi-core Linux CPUs. It handles missing feature fields natively and produces calibrated class probabilities.
Capability 3: Threat & Anomaly Detection:
Model Family: Two-Stage Ensemble:
Stage 1: Rate Threshold Engine: Rapidly identifies high-volume denial-of-service attacks (e.g., deauthentication floods).
Stage 2: Isolation Forest (Unsupervised) + LightGBM (Supervised Multiclass): Isolation Forest detects zero-day protocol anomalies, while LightGBM identifies known AWID3 threat signatures4.
Capability 4: Dedicated Cryptomining Detector:
Model Family: XGBoost Binary Classifier using inter-arrival time autocorrelation and packet size histogram features.
Rationale: Separating cryptomining into a specialized binary detector prevents high-bandwidth activity classes (like streaming) from obscuring low-volume, highly periodic mining signatures.

Definitive Phase 0 Implementation Directives
To successfully support future offline training and real-time inference across fingerprinting, activity classification, and threat detection, the Phase 0 layer must be updated to extract, derive, store, label, and version the following core components:
Extract:
From Management Frames: Ordered Information Element tag sequences, vendor-specific OUIs (Tag 221), HT/VHT/HE capability bitmasks (Tags 45, 191, 255), and 12-bit 802.11 sequence numbers3.
From Frame Headers: To-DS, From-DS, Retry, and Power Management control flags, frame length, signal RSSI, and frequency4.
Control Frame Counters: Enable high-frequency aggregation for RTS/CTS frames22.
Derive:
30-second sliding client activity feature vectors (packet rates, byte rates, mean/median packet size, IAT variance, uplink/downlink byte ratios, burst durations, and autocorrelation periodicity scores)18.
1-second channel threat tick vectors (deauthentication rates, disassociation rates, association failure counts, and sequence gap deltas)4.
Store:
Preserve structured, windowed feature schemas in lightweight local database tables or Parquet files, bypassing full packet payload duplication while retaining necessary layer-2 signals.
Label:
Maintain a labeling database mapping observations to physical device hardware GUIDs, activity classes (idle, browsing, streaming, file_transfer, chat, voip, p2p), threat classes (normal, deauth_flood, rogue_ap, injection), and binary mining flags (mining, non_mining).
Version:
Track dataset schema versions and feature transformation parameters alongside model training metadata to ensure reproducible offline training and compatible online inference.
